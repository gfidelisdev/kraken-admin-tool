### What this proposes
This document proposes adding first-class Microsoft OAuth2 v2.0 Device Code Flow authentication to the Kraken Admin Tool sign-in page alongside an in-memory Backend Token Broker (`MicrosoftSessionBroker`). When an operator signs in with a Microsoft account, Kraken matches their email against local database users (creating a `pending` viewer account requiring admin approval if unrecognized) and, for `active` users, issues a Kraken JWT with a unique session ID (`jti`) while storing their Microsoft `refresh_token` and `access_token` solely in backend memory indexed by `jti`. Frontend and Web Worker plugin contexts receive only non-sensitive metadata (`self.kraken.user`), while authorized plugins (such as `com.kraken.azure-keyvault`) can request short-lived, resource-scoped Microsoft access tokens on demand via a new WASM host bridge function (`kraken_auth_get_token`) and host adapter operation (`auth.get_session_token`). If an operator logs in with a local Kraken account instead, the broker returns no session token and plugins fall back to their existing standalone authentication configurations.

### How the existing system works, per this document
Kraken Admin Tool is a full-stack control plane for managing Docker containers, host servers, and Kubernetes clusters that supports plugins composed of isolated frontend Web Workers (`PluginSurfaceRenderer.tsx`) and backend WebAssembly (WASM) modules executed via a Go Wazero runtime (`WasmHostBridge`). Currently, Kraken authenticates operators exclusively through local database accounts (username, password, and optional TOTP) with RBAC roles and account approval statuses (`active`, `pending`, `rejected`), issuing a 24-hour JWT. Plugins that interact with Microsoft Azure services, such as `com.kraken.azure-keyvault`, must currently run their own separate authentication flows inside the plugin UI and store configuration in `PluginKVStore`, a key-value store keyed only by `plugin_id` and key name that is shared globally across all Kraken users.

1. **Severity**: Nit
   **Affected Scope**: Section `Technical Plan (Architecture)` -> `1. Microsoft Device Code Flow in backend/internal/auth` (line 112) and `Phase 1` -> `4. backend/internal/auth/ms_broker.go` (line 227)
   **Discrepancy Description & Rationale**: Line 112 states that upon token issuance, Kraken extracts identity claims from `id_token` and verifies them via *"an authenticated call to Microsoft Graph (`GET https://graph.microsoft.com/oidc/userinfo`) or token signature/tenant validation"*, and line 227 similarly says *"validates identity via `GET https://graph.microsoft.com/oidc/userinfo` (or token claims `preferred_username`, `email`, `upn`, `name`, `tid`)"*. However, the initial Device Code request in line 109 requests `scope=openid profile email offline_access https://vault.azure.net/.default`, which produces an `access_token` scoped for Azure Key Vault (`https://vault.azure.net`), not Microsoft Graph. Calling `https://graph.microsoft.com/oidc/userinfo` with a Key Vault-scoped access token will fail unless a Graph-scoped token is obtained or `id_token` claim extraction / OIDC validation is used directly. Clarifying the exact primary verification mechanism (and how/whether a Graph token is acquired if `userinfo` is called) will prevent ambiguity during implementation.
